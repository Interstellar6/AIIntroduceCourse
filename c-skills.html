怎么用 Skill

你有没有过这种经历：同一段要求、同一套步骤，反复粘给 AI 好几次？skill 就是为这件事准备的——把「你反复教它的东西」写成一个文件，以后它自己会去用。

一句话：skill 是什么

一个文件夹，里面放一个 SKILL.md，内容就是「遇到这类任务，请按这个流程做」。写完之后：

  • 你可以手动敲 /名字 直接调用它
  • 或者，模型自己在判断「这活儿正好该用它」的时候自动加载

它和「在对话里多写几句要求」最大的区别，在于下面这一点。

💡
skill 是按需加载的 平时，模型只能在上下文里看到 skill 的名字和一句话描述。只有真的要用它的时候，那整份正文才会被加载进来。
所以：你写一份很长的操作手册放在 skill 里，平时几乎不花钱；写在系统提示词里，则是每一轮都在花钱。

它解决什么问题

出现下面任何一种情况，就该考虑写一个 skill：

你在反复粘同一段要求

「按这个格式输出」「先做 A 再做 B，别跳步」——第三次粘贴的时候就该写成 skill 了。

你的操作步骤很长

一份检查清单、一套固定流程、一个多步骤的规程。留在对话里会被压缩掉，写成 skill 就一直在。

你希望每次都按同一套标准来

比如「审代码时必须检查这几项」——写一次，以后每次都会照做。

它长什么样

最简单的形式就是一个文件夹加一个文件：

~/.dsh/skills/
└── review-my-changes/
    ├── SKILL.md          ← 必须有，名字固定
    └── checklist.md      ← 可选：附加的参考资料

文件内容分两部分：上面是 --- 包起来的几行元信息，下面是正文。

---
description: 审查我还没提交的改动，指出风险。当用户问「我改了什么」、
  要写提交信息、或者要审阅自己的 diff 时使用。
---

## 要求

先用 git diff 看一下当前还没提交的改动，然后：

把改动总结成两三条要点，列出你注意到的风险：
缺少错误处理、写死的路径、该补的测试没补。
如果没有任何未提交的改动，就直说。

注意正文里没写「用哪个工具去拿 diff」——它自己会去跑。你只要说清要什么、怎么算合格。

🎯
frontmatter 里最重要的就是 description 因为模型只能看到名字和这句话，然后靠它决定「这个任务该不该用这个 skill」。
写得太笼统（「帮助处理代码」），它就永远不会被触发；写得具体（说清什么场景下用），命中率才高。
描述里写「什么时候用」，比写「它是什么」更重要。

两种触发方式

方式说明
你手动调用 在输入框敲 /，菜单里会列出可用的 skill；敲 /skill-名字 直接调用
模型自己判断 它看到目录里那句 description，觉得跟当前任务对得上，就自己加载

如果你只想让它「由人决定什么时候用」，可以在 frontmatter 里加一行，把它从模型的视野里藏起来：

disable-model-invocation: true

放在哪里

位置决定了它在哪些项目里生效。这是最实用的一张表：

放哪里路径生效范围
个人 ~/.dsh/skills/ DSH
~/.claude/skills/ Claude Code		 你这台机器上的所有项目
项目 项目/.dsh/skills/ DSH
项目/.claude/skills/ Claude Code		 这个项目里的所有会话。提交进仓库，同组的人也能用
共享 / 插件 随插件分发 装了这个插件的所有人
⚠️
路径按工具分，不要混着放 两行不是「二选一随便放哪个」——每个工具只扫自己那个目录：
DSH 只认 .dsh/skills/，它不会去读 .claude/skills/；反过来也一样。
本课程第 2 节课先用 DSH，所以现在统一放 ~/.dsh/skills/ 就行；到第 3 节课装 Claude Code 时，再往 .claude/skills/ 放。

几个容易踩的细节（以 DSH 为例）：

  • 名字必须是 kebab-case：小写字母、数字、中间用连字符，比如 review-changes
  • 两种写法都认：一个文件夹加 SKILL.md，或者一个扁平的 名字.md
  • 项目目录的判定方式是「往上找到最近的含 .git 的目录」，所以你在子目录里启动也能读到项目根目录下的 skill
  • 同名冲突时有优先级：项目里的压过用户目录里的——所以你可以在某个项目里覆盖自己的个人习惯

四个值得学的进阶用法（Claude Code）

📌
先看清楚：这四个是 Claude Code 的写法，DSH 目前不支持 下面四个用法属于 Claude Code 的 skill 规范。你们第 2 节课装的 DSH 只支持三个字段： name、description、disable-model-invocation。
先知道有这些写法就够了——前面讲的原理一个都不少，等第 3 节课装了 Claude Code 再回来用。
课上前 20 分钟只需要会一件事：写一个 SKILL.md，把 description 写具体。

1. 把命令的真实输出直接塞进去

在 skill 正文里写 !`命令`，它会在内容发给模型之前先执行，把输出替换进来：

## 当前改动

!`git diff HEAD`

这样模型拿到的是真实的 diff 内容，而不是靠猜。这正好呼应了Agent 循环那一页的原则：让模型看到上一步的真实结果。

2. 传参数

正文里写 $ARGUMENTS，调用时后面跟的内容就会填进去：

---
description: 按编号修一个 GitHub issue
---

修掉 issue $ARGUMENTS，按我们的代码规范来。

然后 /fix-issue 123 就会变成「修掉 issue 123……」。

3. 让它在一个独立的「分身」里跑

有些 skill 会干很多活、翻很多文件。如果直接在主对话里跑，一堆中间过程会占满上下文。
加一行配置，就能把它丢给一个子代理执行，干完只把结论带回来：

context: fork        # 在一个隔离的上下文里跑
agent: Explore       # 用只读探索型的 agent

4. 预先授权某些命令

有些 skill 每次都要跑 github 命令，而每一步都弹一次审批很烦。可以在 frontmatter 里预先授权：

allowed-tools: Bash(gh *)
⚠️
只对你自己的 skill 这么干。别人仓库里带的 skill 也可能声明了很宽的工具权限——用别人的 skill 之前，先看一眼它写了什么，尤其是 allowed-tools 和里面要执行的命令。

为什么这门课要讲 skill

回到 Harness 那一页说的「一切皆插件」：skill 就是你能用到的最日常的那种「扩展」。你不需要会写代码、不需要改内核，只要写一个 Markdown 文件，就改变了这个 Agent 的行为。

你已经在用的两个层次区别
把结论写进文件
（会话与上下文那一页）		 让 AI 记住事实。「这个项目用 DeepSeek，Key 在 xxx」
把流程写成 skill
（就是这一页）		 让 AI 记住怎么做。「每次读完论文，都要按这个格式给我一份笔记」

两者合起来，就是「不用每次都从零教它」的完整办法。

你现在就可以写的三个 skill

不用等学完，今天就值得写：

读论文的固定流程

让它读完 PDF 后，必须输出：核心问题、方法、实验结果、局限、我不懂的地方。
正好对应任务四。

跑实验的固定步骤

先跑哪个脚本、结果存到哪、失败时先看什么日志。
下次换台机器，它也能照着做。

交作业前的自查清单

格式对不对、引用全不全、有没有跑过一遍、有没有写清 AI 使用声明。

三个常见误区

误区实际上
「description 随便写写，反正我能手动调用」 写得笼统，自动触发就永远不会发生——你会白白丢掉一半的价值
「skill 越多越好」 每个 skill 的名字和描述都常驻在上下文里，装太多会白占地方，也会干扰模型的判断。只留真正常用的
「skill 就是一段长一点的提示词」 它更像一份放在抽屉里的操作手册：平时只有标签露在外面，用到才抽出来
🔍
一个立刻能做的动作 打开你已经装好的工具，敲一个 / 看看菜单里有什么。很多工具出厂就带了一批 skill（比如 /code-review、/debug 这类），它们会告诉你「一个 skill 用起来是什么感觉」。
看懂了再自己写一个，就顺理成章了。
