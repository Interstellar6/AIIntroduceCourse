三种经典范式：ReAct · Plan-and-Solve · Reflection

上一页讲的 Agent 循环是骨架，但骨架里每一步具体该怎么组织——先想还是先做？一口气做完还是边走边看？做完就交还是再改一遍？——业界总结出了三种经典范式。看懂这三种，你会立刻明白很多产品功能为什么长成那个样子。

先说说要解决什么问题

把模型接上工具之后，事情并不会自动变好。智能体会遇到三类典型麻烦：

  • 幻觉——模型凭记忆编事实，而不是去查
  • 推理循环——在复杂任务里绕圈，反复做同一件事
  • 工具误用——调错工具、传错参数，还不知道自己错了

为了组织好「思考」与「行动」这两件事的关系，出现了几种有代表性的范式。下面三种是最经典的，也是后面所有 Agent 工具的底子。

范式一句话提出
ReAct 边想边做，每一步都看结果 Yao 等，2022（ICLR 2023）
Plan-and-Solve 先出完整计划，再逐步执行 Wang 等，2023
Reflection 先做出来，再批判，再改 Shinn 等，2023（NeurIPS）

一、ReAct：边想边做

在 ReAct 出现之前，主流方法分两类：一类是纯思考，比如思维链（Chain-of-Thought）——能推理，但无法与外部世界交互，容易产生事实幻觉；另一类是纯行动——直接输出要执行的动作，但缺乏规划和纠错能力。

ReAct 的洞察是：思考与行动本来就是相辅相成的。思考指导行动，而行动的结果又反过来修正思考。

它用一套固定的输出格式来强制这个过程，每一步都遵循同一套轨迹：

要素是什么
Thought（思考）智能体的「内心独白」：分析当前情况、分解任务、制定下一步计划，或者反思上一步的结果
Action（行动）决定采取的具体动作，通常是调用一个工具，比如 Search[华为最新手机]
Observation（观察）执行 Action 之后，工具返回的真实结果

不断重复 思考 → 行动 → 观察 这个循环，每次把新的观察追加到历史里，直到模型在思考中认为已经找到答案，就输出 Finish[最终答案]。

🎯
一句话概括它的价值：推理让行动更有目的性，行动给推理提供事实依据。

它适合什么任务

  • 需要外部知识的：查实时信息（天气、新闻、股价）、搜索专业领域的知识
  • 需要精确计算的：把数学交给计算器工具，避免模型算错
  • 需要与 API 交互的：操作数据库、调用某个服务完成特定功能

共同点：你事先不知道要走几步，必须看一步走一步。

二、Plan-and-Solve：先谋后动

如果说 ReAct 像一个经验丰富的侦探，根据现场的蛛丝马迹一步步推理、随时调整调查方向；那么 Plan-and-Solve 更像一位建筑师——动工之前必须先画出完整的蓝图，然后严格按照蓝图施工。

它把流程拆成两个解耦的阶段：

  1. 规划阶段

    接到问题后，智能体的第一个任务不是直接去解决或调工具，而是把问题分解，制定出一份清晰的分步计划。这份计划本身就是一次模型调用的产物。

  2. 执行阶段

    拿到完整计划后，严格按照计划逐步执行。每一步可能是一次独立的模型调用，也可能是对上一步结果的加工，直到所有步骤完成。

它要解决的问题是：思维链在处理多步骤复杂问题时，很容易「偏离轨道」——走着走着就忘了原来的目标。先出计划再执行，可以让智能体保持更高的目标一致性。

它适合什么任务

  • 多步数学应用题：先列出计算步骤，再逐一求解
  • 需要整合多个信息源的报告：先规划好结构（引言、来源 A、来源 B、总结），再逐一填充
  • 代码生成：先构思好函数、类、模块的结构，再逐一实现

共同点：路径基本确定，重推理而不是重探索。

⚠️
它的软肋 计划是一次性生成、不可修改的。如果执行到中途发现某个步骤做不了、或者结果不符合预期，它不会自己回头改计划——这是它和 ReAct 最大的差别。

三、Reflection：做完再批判一遍

前两种范式都在解决「怎么把事做出来」。Reflection 解决的是另一个问题：做出来的东西不够好，怎么办？

它把一次性的任务执行，变成一个持续优化的过程——执行 → 反思 → 优化，循环若干轮：

  • 执行：先拿出一个初稿
  • 反思：扮演「严格的评审员」，批判性地分析初稿，给出具体的、可操作的改进意见
  • 优化：结合任务、上一版稿子和评审意见，产出新版本

终止条件是：评审意见里说「无需改进」，或者达到预设的最大迭代次数。

一个真实例子：写一个找素数的函数

这个例子很能说明问题，因为它的优化路径非常清晰：

轮次发生了什么
初稿 模型写出一个用试除法的实现，功能正确，时间复杂度 O(n√n)
第 1 轮反思 评审角色指出：每个数都要试除，n 大时性能显著下降，建议改用埃拉托斯特尼筛法，复杂度降到 O(n log log n)
第 1 轮优化 按建议重写为筛法实现
第 2 轮反思 评审认为筛法已经足够高效，还顺便提到了分段筛法等更高级的方向，但结论是「一般情况下无需改进」——触发终止

注意第二轮：它没有为了改而改。判断「已经够好了」并停下来，和发现问题一样重要。

它的价值，以及它的代价

价值

它提供了一个内部纠错回路——不再完全依赖外部工具的反馈，因此能修正更高层次的逻辑和策略错误。

它把「合格」的初稿，迭代成「优秀」的成品。

代价

每轮至少多调用两次模型（一次反思、一次优化），成本和耗时成倍增加。

整个流程是串行的，延迟明显，不适合要快速响应的场景。

⚖️
Reflection 是一种典型的「以成本换质量」策略。适合那些对最终结果质量要求极高、对实时性要求宽松的场景。
反过来，如果只是要一个「大致正确」的答案，用更轻量的 ReAct 或 Plan-and-Solve 更划算。

三者对比：什么时候用哪个

范式它怎么组织核心优势适合
ReAct 边想边做，每一步都看真实的观察结果 环境适应性、动态纠错 探索性任务、需要外部工具输入
Plan-and-Solve 先一次性出完整计划，再逐步执行 结构性、稳定性、目标一致性 逻辑路径确定、内部推理密集
Reflection 先做出来，再批判，再改，循环若干轮 最终质量显著提升 对准确性和可靠性要求极高、时间不紧

三者不是互斥的。真实产品里往往是组合使用——比如先用 Plan-and-Solve 定框架，执行每一步时内部用 ReAct，最后对关键产出做一轮 Reflection。

它们和你接下来要装的东西是什么关系

这一页听起来很「理论」，但你会立刻在界面上撞见它们。这三种范式回答的其实是同一个问题：Agent 循环里的每一步，该怎么组织。

你在产品里看到的它就是
Agent 默认的「边做边看报错、自己改」 ReAct——几乎所有 Agent 工具的默认行为
DSH 的计划模式：先出方案给你批，批了才动手 Plan-and-Solve 的产品化形态
DSH 的目标模式：给个长期目标，它自己一轮轮做 Plan-and-Solve 的长期版本
