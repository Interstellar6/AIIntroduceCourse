怎么跟 Agent 说话

上一页讲了 Agent 和聊天框的差别。这一页讲一个更实际的问题：知道它是什么之后，第一句话该怎么说？跟 Agent 说话的方式和跟聊天框很不一样——因为它会动手，说错了代价不一样。

它不知道的三件事

大部分「它怎么这么笨」的时刻，其实是你漏说了下面某一件事：

它看不到你的屏幕

你在想什么、你刚才试过什么、哪个文件是相关的——它一概不知道，除非你说，或者它自己去翻。

它不知道你的「好」是什么标准

「优化一下」是快？是短？是省内存？是更好懂？你说不清，它就只能自己挑一个。

它不知道哪些东西碰了会出事

哪个文件不能动、哪个目录里是重要数据、哪条命令跑了就回不来——它没有这个常识。

所以好的第一句话，本质上是在补上这三个缺口。

三件事：目标、边界、验收

要素回答什么问题反例
目标 你要的结果是什么（不是你要它做哪些动作） 「把这段改改」
边界 能碰什么、绝对不能碰什么 （大多数人根本不提）
验收 怎么算做完了？跑什么能证明它是对的？ 「做好一点」

第三项是最容易被忽略、也最有用的。如果你能说出一条「跑完看到什么就算成功」的命令，就一定要说出来。它不只是帮你验收，还会直接改变它的做法——因为它知道最后要被检验。

一个可以套用的骨架

目标：一句话说清你要的结果
位置：相关的文件 / 目录在哪
验收：跑什么、看到什么就算对
边界：不要动什么

填进去大概长这样：

data/ 目录下有三个 csv，列的顺序不一样，但表头含义相同。
把它们合并成一个 merged.csv，统一列顺序，在报告里告诉我
你按什么规则对齐的列。

验收：merged.csv 的行数应该等于三个文件行数之和，
     用 python 读一遍确认没有空行和数据错位。

边界：不要改 data/ 里的原始文件。

对比一下同一件事的另一种说法：「帮我把这几个 csv 合并一下」。

后者也能跑起来，但你会得到：列对错了你不知道、原始文件被覆盖了、行数少了几十行也没人告诉你。省下的那两行字，要用三轮来回补。

好一点的说法 vs 差一点的说法

差一点好一点差在哪
帮我改改这个代码 src/parser.py 里 handle_input 遇到空字符串会崩，修掉它，然后跑 pytest tests/test_parser.py 确认通过 给了位置、现象、验收方式
优化一下这个函数 把 find_primes 的时间复杂度从 O(n√n) 降到 O(n log log n)，输出必须和现在完全一致 「优化」是个没有标准的词，换成可验证的目标
帮我写个脚本 写个脚本，把 logs/ 下所有 .log 里含 ERROR 的行抽出来按日期汇总。用 Python，依赖越少越好 补上了输入在哪、输出是什么、约束是什么
它还是不行 （见下一节） 这句话里没有任何信息

反馈的质量，决定结果的质量

这是整页最重要的一节。Agent 是靠真实结果来修正自己的，你反馈的信息量直接决定它能不能改对。

什么算「完整的反馈」

一句话里尽量包含这三样：

  1. 我做了什么

    「我按你说的跑了 python snake.py」

  2. 我看到了什么

    把真实的输出或报错整段贴出来，不要只挑一行

  3. 我期望什么

    「我以为会出现游戏画面，结果窗口一闪就没了」——很多人会漏掉这一句

🚫
不要说「还是不行」 这四个字对它来说等于零信息。它只能靠猜——而它一旦开始猜，你就要陪着它猜很多轮。

什么时候说步骤，什么时候别说

一个常见的误区是：把每一步都指挥得死死的。这通常会让结果更差。说清目标和验收，把「怎么做」留给它——它能看到你看不到的报错，随时调整。

但有三种情况必须你来说：

情况你该怎么说
顺序有严格要求 「必须先备份再改，顺序不能反」
涉及不可逆的操作 「先别动手，把你的计划列出来给我看」——对应计划模式
有必须遵守的规范 「所有输出用中文，代码注释只写为什么、不写是什么」——这类反复出现的要求，更适合写成 skill

和聊天框说话的五个不同

在聊天框里在 Agent 里
粘贴代码片段 说路径。「src/app.py 的第 3 个函数」比粘贴整段代码更有效，因为它能自己去看、还能看到上下文
想问什么问什么 先划边界。它会真的动手，所以「不要动 X」和「要做什么」一样重要
你复制报错给它 让它自己跑。它就在你的电脑上，能拿到第一手的报错，比你转述的完整
一问一答 一次可以给一个完整任务。它一轮里能连着做几十步，不用你一句话指挥一个动作
关掉网页就没了 相关的东西要在一起。要么放在同一个目录里让它看到，要么写进文件

迭代：一轮一轮来

跟 Agent 干活不是一个「写对提示词」的动作，而是一个来回的过程：

  1. 给任务和目标

    用它第一句话的骨架。不要一开始就把所有细节说完——你不确定它会遇到什么。

  2. 自己先看结果

    别急着夸也别急着骂。跑一遍、打开文件看一眼，你才知道真实情况是什么。

  3. 反馈真实差距

    用上面那三样：我做了什么、看到什么、期望什么。

  4. 连续卡住三次，就改需求

    这一条最反直觉，也最省时间——见下。

🔁
「卡住三次就改需求」是什么意思

如果它在同一个问题上失败了三轮，问题多半不在它的实现，而在于你给的要求本身有问题——可能是目标互相冲突、可能是前提假设不成立、可能是这件事根本做不到。

这时候继续让它「再试一次」，只是在烧钱。换一个更容易达成的目标，或者把任务拆小一点。

改需求，比改代码便宜得多。

五句可以立刻用起来的话

说法什么时候用
「先别动手，把你的计划列给我看」 任务比较大、或者会动到重要文件时
「做完之后跑一遍 X，把输出贴给我」 你希望它自己验证，而不是嘴上报个「完成了」
「有不确定的地方先问我，不要自己猜」 需求里有你才知道的信息时
「只改这个文件，其他都不要动」 想缩小影响范围的时候
「说说你为什么这么做」 它给的方案你看不懂、或者想顺便学点东西

一个反直觉但很有用的建议：说「为什么」

很多时候，告诉它动机比告诉它要求更有用。因为它可以据此做出你没说出口的取舍。

只说要求加上动机
「给这个函数写注释」 「我要交作业，老师会挨个问每行代码在干什么」
→ 它会写解释性的注释，而不是复述代码
「把这段改快一点」 「这个函数每次实验要跑几百万次」
→ 它会去关注算法复杂度，而不是微调写法
「整理一下这些数据」 「我要用这些数据画图放进论文里，所以要能说明每个数字从哪来」
→ 它会保留来源，而不是直接覆盖原文件

四个常见错误

错误后果
一句话里塞十个任务 它做完前两个就忘了后面。拆成几个任务，或者让它先列个清单
把它当搜索引擎 「XX 是什么意思」这种问题，用聊天框更快更便宜。Agent 的价值在动手
不给验收标准就要求「做好一点」 它会给你一个它认为的「好」，然后你们对「好」的理解不一致，来回扯
你自己还没想清楚要什么 这一条无解。先花两分钟把目标写下来，比多来回十轮便宜
🧠
一句话总结这一页 跟 Agent 说话，与其说是「写提示词」，不如说是在派活：
说清要什么、划清范围、给出验收方式，然后把怎么做留给它。
